# Bomb Arena — Protocol v1

서버와 클라이언트가 공유하는 통신 규약입니다.
**양쪽이 각자 직렬화 방식을 추정하지 않도록, 모든 필드의 자료형·순서·길이를 이 문서에서 확정합니다.**

| 항목 | 값 |
|---|---|
| 버전 | `1` (문서 개정 `1.1`) |
| 전송 | TCP |
| 서버 주소 | `127.0.0.1:9000` (개발 기준) |
| 최종 수정 | 2026-09-06 |

## 구현 상태

이 문서는 **확정된 규약**이며, 서버 구현 상태는 아래와 같습니다.

| 구간 | 패킷 ID | 서버 구현 |
|---|---|---|
| 채팅 (기존) | 1, 2, 3, 4, 1000, 1001 | **구현 완료** |
| 접속·방·준비 | 10, 11, 20, 21, 22 | **구현 완료** |
| 매치 시작 | 30 | **구현 완료** |
| 오류 | 1002 | **구현 완료** |
| 게임 진행 | 31, 32, 33, 34 | 미구현 |

**서버는 미구현 패킷 ID를 알 수 없는 패킷으로 판정하여 `SC_KICK`(1001)을 보내고 연결을 끊습니다.**
따라서 현재 서버에 `CS_INPUT`(31)을 보내면 강제 종료됩니다.

대기실 구간(접속 → 방 입장 → 준비 → 매치 시작)은 Unity 클라이언트와 실제로 연동되어 동작합니다.
게임 진행 구간(31~34)은 고정 주기 틱 루프·충돌 판정·폭발 전파가 필요하므로 다음 단계로 분리했습니다.

구현 순서는 위 표의 위에서 아래입니다.

---

## 1. 프레이밍

모든 패킷은 **4바이트 헤더**로 시작합니다.

```text
+--------+--------+--------+--------+------------------+
|     size (u16)  |      id (u16)   |      body        |
+--------+--------+--------+--------+------------------+
 0        1        2        3        4 ...
```

| 필드 | 자료형 | 의미 |
|---|---|---|
| `size` | `uint16` | **헤더를 포함한 전체 길이.** body만의 길이가 아닙니다 |
| `id` | `uint16` | 패킷 ID |
| `body` | 가변 | `size - 4` 바이트 |

- **최대 패킷 크기는 4096바이트**입니다. `size`가 4 미만이거나 4096 초과이면 서버가 연결을 끊습니다.
- body가 없는 패킷은 `size = 4`입니다.

### 스트림 처리 규칙

TCP는 패킷 경계를 보존하지 않습니다. 수신 측은 반드시 이렇게 처리합니다.

1. 수신 버퍼에 4바이트 미만이면 **대기**
2. 헤더를 읽어 `size`를 확인 (소비하지 않음)
3. 버퍼에 `size` 바이트 미만이면 **대기**
4. `size` 바이트를 꺼내 한 패킷으로 처리
5. 남은 데이터로 1번부터 반복 — **한 번의 수신에 여러 패킷이 붙어 올 수 있습니다**

## 2. 공통 인코딩 규칙

| 규칙 | 내용 |
|---|---|
| 바이트 순서 | **little-endian** (모든 정수) |
| 구조체 패딩 | **의존 금지.** 필드를 하나씩 명시적으로 직렬화합니다 |
| 문자열 | `uint16` 바이트 길이 + UTF-8 바이트열. **널 종료 문자 없음** (예외는 아래 참조) |
| 배열 | `uint16` 원소 개수 + 원소 반복 |
| 불리언 | `uint8` (0 = false, 그 외 = true) |
| 좌표 | `int32`. **타일 한 칸 = 1000 단위** |

> **문자열 규칙의 예외.** 기존 채팅 패킷 `CS_LOGIN`(1)과 `CS_CHAT`(2)은 이 규칙을 따르지 않습니다.
> 두 패킷은 **길이 접두어 없이 body 전체를 문자열로 취급**합니다. 기존 클라이언트 호환을 위해 v1에서 유지합니다.
> 위 표의 규칙은 **신규 패킷(10 이상)에만** 적용됩니다.

### 자료형 표기

| 표기 | 크기 | 범위 |
|---|---|---|
| `u8` / `i8` | 1 | 0~255 / -128~127 |
| `u16` / `i16` | 2 | 0~65535 / -32768~32767 |
| `u32` / `i32` | 4 | |
| `str` | 2 + N | 길이(u16) + UTF-8 N바이트 |

## 4. 패킷 상세

### 1 · `CS_LOGIN` (구현됨)

```text
body: [name: str]
```

body 전체가 닉네임입니다. **현재 구현은 길이 접두어 없이 body 전체를 이름으로 읽습니다.**
v1에서는 이 동작을 유지합니다 — 기존 클라이언트 호환을 위해서입니다.

### 2 · `CS_CHAT` (구현됨)

```text
body: 메시지 UTF-8 바이트 (길이 접두어 없음, body 전체)
```

### 3 · `SC_CHAT` (구현됨)

```text
body:
  senderId : u32
  nameLen  : u16
  name     : nameLen 바이트 (UTF-8)
  msgLen   : u16
  msg      : msgLen 바이트 (UTF-8)
```

발신자 본인에게는 전송되지 않습니다. 같은 방의 다른 참가자에게만 갑니다.

### 4 · `CS_ENTER_ROOM` (구현됨)

```text
body: [roomId: i32]
```

### 10 · `CS_HELLO`

```text
body: [protocolVersion: u16]
```

접속 직후 **가장 먼저** 보내야 합니다. 서버는 버전이 맞지 않으면 `SC_ERROR`를 보내고 끊습니다.

### 11 · `SC_WELCOME`

```text
body:
  result     : u8      -- 0 = 성공, 그 외 오류 코드
  playerId   : u32     -- 이 접속에 부여된 고유 ID
  serverTick : u32     -- 서버 현재 틱 (시간 기준 맞추기용)
```

### 20 · `CS_JOIN_ROOM`

```text
body: [roomId: i32]
```

`roomId = 0`이면 **서버가 빈 방을 자동 배정**합니다.

**유효한 방 번호는 1 이상입니다.** 자동 배정을 요청한 경우에도 서버는 응답 `SC_ROOM_STATE`에
**실제로 배정된 1 이상의 방 번호**를 담아야 합니다. 클라이언트는 `roomId <= 0`인 `SC_ROOM_STATE`를
프로토콜 위반으로 처리합니다.

### 21 · `SC_ROOM_STATE`

```text
body:
  roomId    : i32
  capacity  : u8       -- 방 정원 (P0에서는 2)
  count     : u16      -- 아래 배열 원소 수
  players[count]:
      playerId : u32
      isReady  : u8
      nameLen  : u16
      name     : nameLen 바이트
```

참가자가 들어오거나 나갈 때, Ready 상태가 바뀔 때마다 **방 전체에 브로드캐스트**됩니다.

### 22 · `CS_READY`

```text
body: [isReady: u8]
```

**정원이 다 차고 전원이 Ready이면 서버가 게임을 시작합니다.**

### 30 · `SC_GAME_START`

```text
body:
  matchId     : u32
  tickRate    : u16     -- 초당 틱 수 (20)
  tileUnit    : u16     -- 타일 한 칸의 좌표 단위 (1000)
  mapWidth    : u8      -- 타일 개수 (15)
  mapHeight   : u8      -- 타일 개수 (13)
  tiles[mapWidth * mapHeight] : u8   -- 0 = 빈칸, 1 = 벽
  count       : u16
  spawns[count]:
      playerId : u32
      x        : i32    -- 세부 좌표
      y        : i32
```

`tiles`는 **행 우선(row-major)** 순서입니다. 인덱스 `y * mapWidth + x`.

**`spawns`는 직전 `SC_ROOM_STATE`의 참가자 전원을 정확히 한 번씩 포함해야 합니다.**
개수가 다르거나 누락된 참가자가 있으면 클라이언트는 프로토콜 위반으로 처리합니다.

**모든 시작 좌표는 빈칸(`tiles == 0`) 위에 있어야 합니다.** 아래 §5의 맵 규칙을 참조하십시오.

### 31 · `CS_INPUT`

```text
body:
  matchId  : u32
  sequence : u32       -- 클라이언트가 1부터 증가시키는 값
  dir      : u8        -- 0=정지 1=상 2=하 3=좌 4=우
```

**중요.** 서버는 이 패킷을 받은 횟수만큼 이동시키지 않습니다.
**마지막 방향만 보관했다가 틱마다 정해진 양만 적용**합니다. 따라서 패킷을 빨리 보내도 빨라지지 않습니다.

`sequence`는 서버가 스냅샷에 되돌려 보내 클라이언트가 처리 상태를 확인하는 용도입니다.

### 32 · `CS_PLACE_BOMB`

```text
body:
  matchId  : u32
  sequence : u32
```

**좌표를 보내지 않습니다.** 서버가 요청자의 현재 위치에서 설치 타일을 결정합니다.

### 33 · `SC_SNAPSHOT`

```text
body:
  matchId   : u32
  tick      : u32

  pCount    : u16
  players[pCount]:
      playerId  : u32
      x         : i32
      y         : i32
      alive     : u8
      lastSeq   : u32   -- 서버가 마지막으로 처리한 CS_INPUT sequence

  bCount    : u16
  bombs[bCount]:
      bombId    : u32
      ownerId   : u32
      tileX     : u8
      tileY     : u8
      explodeAt : u32   -- 폭발 예정 틱

  eCount    : u16
  explosions[eCount]:
      tileX     : u8
      tileY     : u8
      endTick   : u32   -- 소멸 예정 틱
```

**같은 방 전원에게 전송되며, 요청자 자신도 포함**합니다.
P0에서는 델타 없이 매 틱 전체 상태를 보냅니다.

### 34 · `SC_GAME_RESULT`

```text
body:
  matchId  : u32
  outcome  : u8        -- 0=무승부 1=승자 있음
  winnerId : u32       -- outcome이 0이면 0
  reason   : u8        -- 1=피격 2=상대 이탈 3=시간 초과
```

이 패킷 이후의 `CS_INPUT`·`CS_PLACE_BOMB`은 **거절되고 `SC_ERROR`가 돌아갑니다.**

### 1002 · `SC_ERROR`

```text
body:
  rejectedId : u16     -- 거절된 요청의 패킷 ID
  code       : u16     -- 아래 오류 코드
```

| 코드 | 의미 |
|---:|---|
| 1 | 프로토콜 버전 불일치 |
| 2 | 잘못된 패킷 크기 또는 형식 |
| 3 | 현재 상태에서 허용되지 않는 요청 |
| 4 | 존재하지 않는 방 또는 매치 |
| 5 | 방 정원 초과 |
| 6 | 매치 종료 후 요청 |
| 7 | 폭탄 동시 설치 한도 초과 |

## 5. 게임 상수

상수는 **패킷으로 전달되는 값**과 **v1에서 고정된 값**으로 나뉩니다.
이 구분을 지키지 않으면 클라이언트가 얻을 수 없는 값을 참조하게 됩니다.

**A. `SC_GAME_START`로 전달됨 — 하드코딩 금지**

| 항목 | 필드 | 기본값 |
|---|---|---|
| 틱 주기 | `tickRate` | 20 (Hz) |
| 타일 단위 | `tileUnit` | 1000 |
| 맵 크기 | `mapWidth`, `mapHeight` | 15 × 13 |
| 맵 구조 | `tiles` | §5 맵 레이아웃 참조 |
| 시작 위치 | `spawns` | §5 시작 위치 참조 |

**B. v1 고정값 — 패킷으로 전달되지 않음. 양측이 아래 값을 그대로 사용**

| 항목 | 값 | 비고 |
|---|---|---|
| 이동 속도 | 3500 units/초 | 틱당 175 units = 타일의 17.5% |
| 플레이어 히트박스 | 600 × 600 units | 중심에서 ±300. 타일보다 작아 모서리 통과 가능 |
| 폭탄 타이머 | 60틱 (3초) | |
| 폭발 지속 | 10틱 (0.5초) | |
| 폭발 범위 | 중심 + 상하좌우 각 2타일 | 벽에 막힘 |
| 동시 설치 | 플레이어당 1개 | |
| 입력 타임아웃 | 10틱 (0.5초) | 갱신이 없으면 정지 |

> **B군은 v2에서 `SC_GAME_START`로 옮길 예정입니다.** v1에서 전달하지 않는 이유는
> 클라이언트가 이미 A군 기준으로 구현·검증을 마쳤고, 패킷 레이아웃 변경이
> 검증된 코드를 무효화하기 때문입니다. 서버는 B군 값을 소스에 상수로 두되
> **한 곳에 모아** v2 전환 시 그대로 직렬화할 수 있게 합니다.

### 좌표계

- **원점은 좌상단**, x는 오른쪽, y는 아래쪽 증가
- 타일 `(tx, ty)`의 중심 좌표는 `(tx * 1000 + 500, ty * 1000 + 500)`
- 좌표 `(x, y)`가 속한 타일은 `(x / 1000, y / 1000)` (정수 나눗셈)

### 맵 레이아웃 (P0 고정)

```text
외곽 한 줄은 전부 벽
내부에서 x와 y가 모두 짝수인 타일은 벽
그 외는 빈칸
```

> **개정 1.1 정정.** 초판은 이 규칙을 "모두 홀수"로 잘못 기재했습니다.
> 홀수 규칙에서는 시작 위치 (1,1)과 (13,11)이 **모두 벽 안에 놓여** 게임이 성립하지 않습니다.
> 클라이언트 구현 과정에서 발견되어 정정하였습니다.

15 × 13 기준 실제 맵 (`#` = 벽, `1`·`2` = 시작 위치):

```text
###############
#1............#
#.#.#.#.#.#.#.#
#.............#
#.#.#.#.#.#.#.#
#.............#
#.#.#.#.#.#.#.#
#.............#
#.#.#.#.#.#.#.#
#.............#
#.#.#.#.#.#.#.#
#............2#
###############
```

빈칸 113개, 벽 82개. 두 시작 위치는 각각 두 방향의 탈출로를 가집니다.

15 × 13 기준 시작 위치:

| 플레이어 | 타일 | 좌표 |
|---|---|---|
| 1번 | (1, 1) | (1500, 1500) |
| 2번 | (13, 11) | (13500, 11500) |

### 알 수 없는 패킷 ID

**서버는 게임 세션(`InGame` 상태)에 있는 클라이언트에게 채팅 패킷 `SC_CHAT`(3)을 보내지 않습니다.**
게임 클라이언트는 채팅 패킷을 해석하지 않으며, 수신 시 프로토콜 위반으로 연결을 종료할 수 있습니다.

향후 채팅을 게임 화면에 통합할 경우 이 규정을 개정하고, 클라이언트가 **모르는 ID를 조용히 무시**하도록
먼저 변경해야 합니다. 순서를 바꾸면 기존 클라이언트가 전부 끊깁니다.

### 판정 규칙

**이동** — 틱마다 현재 방향으로 175 units 이동시킨 뒤, 히트박스가 벽 타일과 겹치면 이동을 취소합니다. x축과 y축을 따로 검사해 벽을 스치며 미끄러질 수 있게 합니다.

**폭탄 설치** — 요청자의 **중심 좌표가 속한 타일**에 설치합니다. 그 타일에 이미 폭탄이 있으면 `SC_ERROR` 코드 7을 보냅니다.

**설치자 통과** — 설치 직후에는 그 폭탄을 통과할 수 있습니다. **설치자의 히트박스가 그 타일에서 완전히 벗어난 순간부터** 폭탄이 벽으로 취급됩니다.

**폭발 전파** — 중심 타일에서 상하좌우로 한 칸씩, 최대 2칸까지 진행합니다. 벽을 만나면 그 방향은 즉시 멈추고 벽 타일은 폭발 영역에 포함되지 않습니다.

**피격** — 플레이어 히트박스와 폭발 타일 영역이 **겹치면** 피격입니다. 경계에 정확히 닿기만 한 경우(면적 0)는 피격이 아닙니다.

**동시 피격** — 같은 틱에 양쪽이 피격되면 **무승부**(`outcome = 0`)입니다.

## 6. 상태 전이

```text
   [접속]
      │ CS_HELLO
      ▼
   [인증됨] ──────────── SC_WELCOME
      │ CS_JOIN_ROOM
      ▼
   [방 안]  ◄──────────► SC_ROOM_STATE (변경 시마다)
      │ CS_READY (전원 준비)
      ▼
   [게임 중] ─────────── SC_GAME_START, 이후 매 틱 SC_SNAPSHOT
      │                  CS_INPUT / CS_PLACE_BOMB 허용
      │ 승패 확정
      ▼
   [종료]   ──────────── SC_GAME_RESULT
                         CS_INPUT / CS_PLACE_BOMB 거절 (SC_ERROR 6)
```

**각 상태에서 허용되지 않는 패킷은 처리하지 않고 `SC_ERROR` 코드 3을 보냅니다.**
클라이언트는 응답을 받은 뒤 다음 단계로 진행하며, **임의의 지연 시간으로 성공을 추정하지 않습니다.**

### 중도 이탈

게임 중 한쪽 연결이 끊기면, 서버는 남은 참가자에게 `SC_GAME_RESULT`(`reason = 2`)를 보내고 매치를 종료합니다.

## 7. 클라이언트 구현 시 주의

1. **좌표를 서버에 보내지 않습니다.** 방향과 sequence만 보냅니다.
2. **서버 좌표를 보간해서 표시합니다.** P0에서는 클라이언트 예측을 하지 않습니다.
3. **입력은 변화가 있을 때만 보내되**, 최소 초당 2회는 갱신하십시오. 0.5초간 갱신이 없으면 서버가 정지시킵니다.
4. **`SC_GAME_START`로 전달되는 값(§5-A)은 반드시 패킷에서 읽으십시오.** 틱 주기·타일 단위·맵 크기·맵 구조·시작 위치를 하드코딩하면 서버 설정 변경 시 어긋납니다. §5-B의 값은 v1에서 전달되지 않으므로 문서의 값을 사용하되, **한 곳에 상수로 모아** v2에서 패킷 수신으로 교체할 수 있게 두십시오.
5. **패킷 조립·분해를 직접 검증하십시오.** 헤더의 `size`가 헤더를 포함한다는 점, little-endian이라는 점이 흔한 실수 지점입니다.
